A terminal execution's canonical result is now durably recorded, keyed by tenant and traversal, so `GET /v1/executions/{id}` and `ravenroot result` answer correctly after a restart and from another instance sharing the same store, wherever a durable, result-capable store is composed — before this, a result lived only in the process that ran it and read back as unknown once that process restarted. A payload's fate is now one of four explicit states instead of a nullable field: produced and kept, produced but refused for exceeding the store's byte cap, produced but not representable in the closed payload model, or never produced at all — the byte cap and the projection's own 16 KiB bound together mean the refused-for-size case is not one you will see at default settings. Recording a terminal result for a traversal id that already has one is idempotent for an identical re-delivery and refused, not merged, for a genuinely different outcome: reusing an execution id across two submissions means the **first** submission's result is what every later read returns, permanently, however the second submission ended.

**Breaking, in one way.** `ExecutionLookup` gains a fourth sealed member, `Redacted`, reported for a terminal execution whose payload was never retainable (refused for size, or unrepresentable) rather than folding it into `Found` with a null payload as before. A consumer that switches exhaustively over `ExecutionLookup` outside this repository stops compiling and must add an arm; a switch with a default arm needs no change. The safe default mapping is the same one `Expired` already gets — status and termination reason present, payload absent — and `Redacted` must never be mapped to `Unknown`, which would report a real, completed execution as one that never happened. On the wire, the equivalent `410` response for this case now carries its own code, `EXECUTION_RESULT_REDACTED`, distinct from `EXECUTION_RESULT_EXPIRED`, plus a `payloadState` field naming which refusal applies; a client that previously treated every `410` on this route identically should distinguish the two codes to tell a size limit it can raise from a value it cannot ever expect to receive.
