# Durable execution results

A terminal execution's canonical result, keyed by tenant and traversal, kept in the configured store instead of only in one process's memory.

## Invariants

- A terminal output crosses one admission boundary before either the process-local result cache or a durable adapter can retain it. The boundary projects the engine's JVM object onto the same closed, redacted and bounded representation used by authenticated runtime activity, encodes that representation as canonical JSON, and produces one immutable `ExecutionResultPayload`. The cache and `DurableExecutionResult` consume that exact decision; neither retains the engine object or projects a competing copy.
- The effective per-result byte cap is the smaller of `GraphExecutionLimits.payload.maxEncodedBytes` and the result-capable store's advertised cap. `RAVENROOT_GRAPH_MAX_PAYLOAD_BYTES` therefore applies when the execution store is disabled as well as when it is enabled, while an adapter may tighten the limit required by its storage medium. An exact-size encoding is retained; one byte beyond the effective cap is withheld in full.
- A payload has exactly four possible fates, and each is its own state, never a nullable field: `NONE` (nothing was produced), `RETAINED` (the projection is present, possibly redacted or truncated), `WITHHELD` (a payload existed and a configured budget refused all of it — either an encoded projection larger than the adapter's published byte cap, whose size is still reported, or a value the runtime's own payload boundary rejected before any encoding of it existed, which carries no size), and `UNCONVERTIBLE` (the value does not project onto the closed payload model at all, whether that was decided at the store boundary or by the payload boundary the traversal terminated on). A fifth, `EXPIRED`, is derived from a record's age at read time and is never written down.
- A read answers in exactly four states, and every one of them maps a real record to a real answer. `Found` reports a live or terminal execution in full. `Expired` reports a terminal execution whose payload has aged past the retention deadline, with status and termination reason still present. `Redacted` reports a terminal execution whose payload was never retainable — `WITHHELD` or `UNCONVERTIBLE` only — with status and termination reason still present. `Unknown` reports that this process holds no record for the id, for any reason, including another tenant's execution. Nothing that exists is ever reported as `Unknown`.
- Recording is idempotent by refusal, never by overwrite. An identical re-delivery of a terminal result is a no-op; a genuinely different outcome for a traversal id that already has a recorded result is refused, naming both digests, and the committed record is left untouched.
- A result's retention window must never exceed its process instance's terminal-retention window, because a result names the instance and traversal it belongs to. Both bundled adapters enforce this at construction, refusing to start otherwise.

## Runtime relationships

- `GET /v1/executions/{id}` answers from the process-local result cache without consulting the store in exactly one case — an execution that has not finished — and defers to the durable record for every terminal answer, the cache's own warm result included. So a result readable before a restart is readable after one, readable from a second instance that never ran the traversal, and stops being served by the instance that ran it at the same moment it stops being served anywhere else. The cache is bounded by a count of executions and not by time, so a warm entry cannot observe a retention deadline without asking; asking is what it does, at the cost of one store read per terminal read, and a caller polling an execution still in flight pays nothing. All of that holds only where a durable, result-capable store is composed. Without one, the restart gap this feature closes reopens: a result readable before a restart still reads as unknown afterward.
- A cache hit decodes a fresh Java view from the admitted bytes. Mutating the object returned by one read cannot change a later read, and mutating the engine's original result after completion cannot change either. This bounds canonical result retention; engine futures and completion callbacks may still hold transient references while they settle and are outside the result cache's retention contract.
- `EXECUTION_RESULT_EXPIRED` and `EXECUTION_RESULT_REDACTED` are both `410`, because both describe the identical shape of absence to an HTTP caller — the resource is known and its content is withheld — and are told apart by the closed-vocabulary code, not by the transport status. The redacted body additionally carries `payloadState` (`WITHHELD` or `UNCONVERTIBLE`), so a caller can tell a size limit an operator may raise from a node returning a value no remote adapter could ever persist. Both fields travel beside the terminal `status` and `terminationReason` for the same reason they do on the `200` body: `status` alone past either boundary reports a cancelled execution as a failure.
- Reusing a traversal id across two submissions does not make the second submission's outcome the one that gets read. The traversal runs to completion either way, but its result is refused at the durable write and never becomes the answer a subsequent read returns — not while the first result's cache entry is warm, not after it ages out, and not after a restart. The first submission's result is what is kept, permanently.
- `AuditedExecutionResultPurge` appends one `ADMINISTRATION` audit record naming the tenant, the count purged, and the operator, whether the purge succeeded or was refused — following the audit trail's own rule that a retention removal is never silent. As of this release, no scheduler, CLI verb, or HTTP route calls the purge; it exists for a caller that composes it directly.

## Architectural consequence

Because a payload's absence is now four distinguishable facts instead of one nullable field, a caller can act on the specific one it received: raise whichever budget refused it, fix a node's return type, or simply accept that a normal run produced nothing. And because the read hierarchy gained a member rather than reusing `Found` with a null payload, that distinction survives all the way to the wire — at the cost of being a breaking change to any exhaustive `switch` over `ExecutionLookup` written outside this repository, which is the price the previous ambiguity would otherwise have kept hidden forever.

`WITHHELD` has two producers and their reachability is not the same. Result admission compares canonical bytes with the effective result cap and retains the exact measured size as bounded metadata, but no payload fragment. At defaults, the author-facing projection's 16 KiB ceiling is below both the graph payload and bundled adapter caps, so a huge value is truncated and retained; lowering `RAVENROOT_GRAPH_MAX_PAYLOAD_BYTES` makes result admission withhold it in both durable and no-store modes. The other producer is a traversal that terminates at an earlier node payload boundary. It records no size because no result encoding was produced. Raising an adapter cap does nothing for that rejection. Multi-instance sharing of the SQLite adapter's file is bounded to processes on one host with a local filesystem — its cross-process exclusion depends on POSIX advisory locks, which are unreliable over a network filesystem, so placing the database there does not degrade the guarantee, it falsifies it.

Admission rejection metrics are identifier-free. `ravenroot.execution.result_payload_rejections` has one finite label, `ravenroot.result_payload_state`, whose only values are `WITHHELD` and `UNCONVERTIBLE`. Tenant, execution, graph and payload data never enter the metric event or its labels.
