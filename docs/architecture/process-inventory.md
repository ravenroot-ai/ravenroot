# Durable process inventory

A tenant-scoped, restart-surviving record of process instances and their traversals, read from the same rows the lifecycle already writes.

## Invariants

- The inventory is served from the authoritative `process_instance`, `traversal`, `invocation`, `attempt`, and `lease` rows the lifecycle transition writes inside one transaction; there is no projection and no repairable offset.
- Pagination orders by `(createdAt descending, processInstanceId descending)`. Both components are immutable per row once set, so a row cannot move between pages of an in-flight scan. Every paginated response also publishes `maxPageSize`, the deployment's declared page-size bound, so a caller does not have to discover it by bisection.
- For a row written before the schema migration that added this inventory, the backfilled `createdAt` is the instant of that row's *last write*, not its true creation instant — a truthful upper bound, stable from the backfill onward, but not history for any instance that existed before the upgrade. Every instance created after the migration carries its real creation instant. `lifecycleGeneration`, reported on every entry, is affected the same way: for a pre-existing row it defaults to `1` as a floor on how many lifecycle transitions the instance has undergone, not an exact count, and is exact only for instances created after the migration.
- A key belonging to another tenant is indistinguishable from one that does not exist, at every read path this inventory exposes.
- A recovery disposition — active, waiting, interrupted, parked, or terminal — is derived at read time under a total precedence with parked ranked highest, and is never itself a stored value.
- There is no durable "paused" disposition, and there is deliberately none even though holds are now durable. A held traversal is durably `WAITING` — the same stored status every other durable wait writes — so a held instance reports `WAITING` here and is therefore ranked above `INTERRUPTED`, which is correct: an instance somebody deliberately stopped is not part of the restart-recovery cohort. Which wait it is comes from the hold record beside the instance, not from a classification this listing invents. A hold taken at a boundary the runtime cannot write down leaves no stored trace at all, and such an instance reports whatever its lifecycle status already was.

## Runtime relationships

- The live-execution view stays what it always was: process-local, in-memory bookkeeping of non-terminal executions, read directly from runtime state rather than from storage. The durable inventory is a separate, tenant-scoped authority read from the store, and it is what remains queryable after the process that ran the work has restarted. Neither view substitutes for the other, and a caller should not have to guess which one answers "what exists."
- A parked attempt outranks even a terminal disposition: an instance can finish while carrying an attempt whose real-world effect outcome was never learned, and the inventory reports that instance as needing operator attention rather than as having nothing left to do.
- The per-tenant retention floor is reported on every inventory listing this store exposes — the paginated process-instance listing and the per-instance traversal listing alike, so a caller has it on whichever one it happens to be holding. It is the *latest* retention deadline the tenant has actually crossed, measured in the same deadline space as each row's own `retainedUntil` — not in creation time. A row whose own deadline sits strictly after the floor is guaranteed still present; a row whose deadline is at or before the floor may have been purged, because the boundary is exclusive — a deadline sitting exactly on the floor is one that was removed. Reading an instance's absence correctly means comparing that instance's own deadline against the floor, not its creation time; the two are different quantities and comparing the wrong one can misclassify a row that is still present.
- Nothing purges automatically. `purgeExpiredProcessInstances` is the operation that advances the retention floor and removes eligible terminal rows, and as of this release no shipped surface — no CLI verb, no HTTP route, no scheduler — calls it. It exists as an interface an embedder composing its own execution store can call. Until something does, the floor stays at its minimum in every real deployment, and every terminal row remains present regardless of age.
- Deployment, workload, and correlation identities are recorded on a row as annotations, not as part of the lifecycle: a write that supplies them sets them, and a write that does not leaves the stored values untouched. They are populated at the two admission paths that know them — transient submission and deployment-hosted ingress — each recording the correlation identity of the request that caused the instance, and deployment-hosted ingress additionally recording its own deployment and the traversal as the owning workload.
- A traversal admitted through the live request/reply ingress contract is not itself covered by this durable record: that ingress path is deliberately live and process-local, and opens no execution recorder of its own. The inventory should not be read as a complete log of every traversal a deployment has ever admitted; it is complete for the admission paths that write to the execution store.

## Architectural consequence

Because the disposition is computed rather than persisted, durable holds arrived without touching this classification at all: no new disposition value, no backfill, and no change to any row already written. A hold is a record beside the instance and a `WAITING` lifecycle status, so the derived answer stayed derived — the same freedom that keeps the inventory from ever needing to reconcile a stored classification against the lifecycle it describes. It did require a schema addition for the hold record itself, which an earlier version of this page predicted it would not; what that prediction got right is the part that mattered here, that no *inventory* row had to change.

The recovery service can discover interrupted instances — non-terminal rows with no live lease — directly from this inventory, as a library method available to code that composes it. As of this release, no shipped surface invokes that discovery path in production: it is not wired to the CLI, the HTTP API, or a scheduler. It exists for an embedder to call, not as an operator-facing capability today. Even once invoked, discovery is all a bare inventory row supports: it carries no attempt identity or fencing token, so acting on what it finds is a separate step.
