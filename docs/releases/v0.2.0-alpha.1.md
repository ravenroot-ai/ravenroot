# Ravenroot 0.2.0-alpha.1

Ravenroot 0.2.0-alpha.1 delivers the work integrated since `0.1.0-alpha.1`. It contains breaking
changes: read *Breaking changes* below before upgrading, together with the compatibility policy and
the operator guides. Pin every Maven and OCI dependency to this exact version, and use an immutable
container digest where deployment reproducibility matters.

## Known issues

- **PostgreSQL JDBC driver 42.7.7.** This release ships the PostgreSQL JDBC driver at 42.7.7 as a
  runtime dependency of the PostgreSQL persistence module (`ravenroot-persistence-postgresql`), which
  `ravenroot-server` includes. That version is affected by CVE-2026-54291 and CVE-2026-42198. The
  release was made knowingly with both; the driver upgrade ships in the next release (#336). The JDBC
  extension (`ravenroot-jdbc`) ships no driver: operators supply their own when they build its bundle,
  and should use a fixed driver version rather than the 42.7.7 artifact in the JDBC bundle reference
  example.

## Breaking changes

- A cancelled execution is now distinguishable from an ordinary failure everywhere it is reported. The durable status stays `FAILED`, exactly as before, but every projection now carries a `terminationReason` (and a `cancelled` convenience flag) beside it: `GET /v1/executions/{id}`'s 200 and 410 bodies, the durable process and traversal inventories on both HTTP and the CLI (`ravenroot result`, `ravenroot inventory`, `ravenroot traversals`), the OpenTelemetry span status (unset rather than an error status), the `ravenroot.execution.events` metric label, the audit trail's own `execution.cancelled` action, and the workspace UI's outcome panel. A cancellation no longer inflates the observed failure rate, and an operator inspecting a `FAILED` run can tell from one field whether it broke or was stopped on request.

  **Breaking, in one way.** The live event stream now publishes `EXECUTION_CANCELLED` for a cancelled traversal instead of `EXECUTION_FAILED`. An external consumer that recognizes only the original two terminal event types will stop seeing a terminal event at all for a cancelled run until it is updated to also handle `EXECUTION_CANCELLED`; the durable status such a consumer may separately read is unaffected and still reports `FAILED`.
- A terminal execution's canonical result is now durably recorded, keyed by tenant and traversal, so `GET /v1/executions/{id}` and `ravenroot result` answer correctly after a restart and from another instance sharing the same store, wherever a durable, result-capable store is composed — before this, a result lived only in the process that ran it and read back as unknown once that process restarted. A payload's fate is now one of four explicit states instead of a nullable field: produced and kept, produced but refused by a configured budget, produced but not representable in the closed payload model, or never produced at all. The refused case has two producers and only one of them is remote — an encoded projection larger than the store's byte cap cannot arise at either bundled adapter's defaults, because the projection's own 16 KiB bound shortens the output before the cap is ever compared against it, while a value the runtime's payload boundary rejects outright terminates the traversal on that rejection, is ordinary at default settings, and is recorded carrying no size at all because no encoding of it ever existed. Recording a terminal result for a traversal id that already has one is idempotent for an identical re-delivery and refused, not merged, for a genuinely different outcome: reusing an execution id across two submissions means the **first** submission's result is what every later read returns, permanently, however the second submission ended.

  **Breaking, in two ways.** First, `ExecutionLookup` gains a fourth sealed member, `Redacted`, reported for a terminal execution whose payload was never retainable (a configured budget refused it, or it does not project onto the closed payload model) rather than folding it into `Found` with a null payload as before. A consumer that switches exhaustively over `ExecutionLookup` outside this repository stops compiling and must add an arm; a switch with a default arm needs no change. The safe default mapping is the same one `Expired` already gets — status and termination reason present, payload absent — and `Redacted` must never be mapped to `Unknown`, which would report a real, completed execution as one that never happened. On the wire, the equivalent `410` response for this case now carries its own code, `EXECUTION_RESULT_REDACTED`, distinct from `EXECUTION_RESULT_EXPIRED`, plus a `payloadState` field naming which refusal applies; a client that previously treated every `410` on this route identically should distinguish the two codes to tell a size limit it can raise from a value it cannot ever expect to receive.

  Second, an execution that terminated on a rejected payload now answers `410 EXECUTION_RESULT_REDACTED` whichever instance is asked. The instance that ran it used to re-raise the retained rejection from the read, which the server rendered as that rejection's own recommended status — `413` for a budget overrun and `400` for a value the payload model cannot represent — so one execution id answered one status while that instance still held it in memory and a different one everywhere else, and every such read left a payload-rejection audit record on that instance and none on any other. A client that special-cased `413` or `400` on `GET /v1/executions/{id}` should read the `410` and its `payloadState` instead: the reason is still distinguishable there, as `WITHHELD` for a budget an operator configures and `UNCONVERTIBLE` for anything no configuration would have admitted.
- A paused execution is now visible to everyone entitled to see it, not only to the caller that paused
  it. The live execution listing and the per-execution read both carry a new `paused` field, always
  present and always `false` for a run nobody has held, so a second operator, a reconnecting client or
  a different session can tell a deliberate hold from a traversal whose behavior has stalled — until
  now those two presented identically, as an execution listed as running that had stopped publishing
  events, and they call for opposite responses. The runtime event stream gains `EXECUTION_PAUSED` and
  `EXECUTION_RESUMED`, published once per transition that actually happened and carrying no node,
  no payload and no caller-supplied text. Pause and resume remain authorized and audited exactly as
  before, and the events travel the same tenant and request attribution as every other execution event,
  so who may observe a hold is decided by the rules that already governed the rest of the stream.

  `paused` is a qualifier on the existing lifecycle `status` rather than a new status value: a hold is
  orthogonal to what the traversal is doing, and collapsing the two would make "held" and "waiting for
  an external decision" indistinguishable. A terminal execution is never reported as paused.

  Pause and resume now have defined behavior when they race the traversal's own end. A traversal that
  has begun to close refuses a new hold, so `EXECUTION_PAUSED` can never appear after an execution's
  terminal event. A hold accepted before the traversal has started is announced only once the execution
  has started, never before it. Cancelling a held execution, the execution completing, and a deployment
  being stopped all release the hold and publish no resume: none of them is the execution running
  again, and reporting one would show a resumption immediately before a permanent stop.

  **Breaking, in four narrow ways.**

  A consumer that switches exhaustively over `ExecutionEventType` in Java must add arms for
  `EXECUTION_PAUSED` and `EXECUTION_RESUMED`; a switch with a default arm, and any consumer reading
  event types as strings, needs no change. Neither new type replaces an existing one, so counts of
  existing event types are unaffected.

  `POST /v1/executions/{id}/pause` now reports `NOT_ACTIVE` in two cases where it previously reported
  `ALREADY_PAUSED`: an execution that has been cancelled, and one that has begun to end. Both were
  wrong before — nothing was holding those executions, and `ALREADY_PAUSED`'s own explanation said a
  hold was in place. The outcome vocabulary is unchanged; a caller that treats `ALREADY_PAUSED` as
  success and `NOT_ACTIVE` as "nothing to do" should re-check that it does not act on the distinction
  in the opposite direction.

  The `ExecutionOutcome` and `LiveExecution` records each gained a component. Both keep a constructor
  with their previous shape, which defaults `paused` to `false`, so existing source and existing
  compiled callers continue to work; code that pattern-matches these records by arity, or that
  constructs them positionally through reflection, must account for the added component.

  The command line's `CliBackend.ResultView` and `CliBackend.LiveView` each gained a component with
  **no** compatibility constructor, and `ResultView` gained it in the middle — at position three, ahead
  of `degraded` — rather than at the end. Anyone implementing `CliBackend` or constructing either view
  must update those call sites; every one of them fails to compile rather than silently changing
  meaning, because the arity changes too. This is scoped narrower than the two records above on
  purpose: the command line is an application, not a published extension point, and these two types
  exist to carry its own output between its own backends. The live listing and the result output each
  print one additional field.
- Ravenroot now classifies the durable work it inherited before it accepts traffic, and recovers an author's repeatability decision from the retained graph document rather than losing it with the process that accepted the execution. On startup a deployment lists its interrupted process instances and, for each, reads back the exact document and execution manifest that instance was accepted against; `GET /ready` answers `503` with the new `RECOVERING` state until that pass completes. A pass that cannot read the store does not complete, so readiness stays closed and it retries; a pass that completes having refused some instances does open readiness, because inherited work this deployment cannot rebuild is an operator fact rather than a reason to stop serving unrelated tenants, and each refusal is reported individually so one damaged instance never hides the rest. Every recovered item now passes through one recovery coordinator with explicitly registered adapters, exactly one of which may own an item, and the coordinator refuses an execution whose document or manifest does not resolve here before any adapter is asked. How long such work is withheld depends on whether waiting could change the answer: durable state that could not be read is waited on indefinitely and consumes no delivery budget, because the budget counts deliveries that reached a decision rather than claims and the withheld ones are recorded durably on the attempt, so an incident spanning a restart still costs it nothing, while a document or manifest that is absent, unverifiable or describes another deployment is withheld for a bounded number of deliveries — a window to correct the deployment — after which an attempt that was already in flight is parked with a cause naming the fault, because it stands for an effect whose outcome nobody knows and withholding that forever is worse than putting the decision in front of an operator. An attempt that had not started is never parked, since it produced no effect to adjudicate. Due timers are outside this gate entirely: closing a durable wait commits store transitions and rebuilds nothing, so tasks still expire and approvals still lapse on an execution this deployment cannot rebuild, while the re-entry an expiry produces is gated like anything else. Recovery is composed wherever a durable store is configured rather than only where durable tool approvals or human tasks are enabled, and transient and deployment-hosted work are classified by the same authority while each keeps its own deployment and workload relationship. Because the retained document is now read back during recovery, an effect whose outcome a crash left unknown is redelivered under its original effect identity when the node declares `recovery.repeatable`, where every such effect previously parked for want of a graph to consult; a node declaring the opposite, or declaring nothing, still parks for a human decision, and a value on a node whose type never declared the property remains inert. One limit bounds what resumes automatically: the durable record holds lifecycle state and not the data passing between nodes, so an interrupted node attempt has no recorded input and is discovered, classified and reported rather than re-executed from an invented one. Work whose committed boundary recorded enough to continue from — a settled handler, a due timer, a tool-approval or human-task continuation, an operator-resumed hold — is unaffected and resumes as before.

  **Breaking, in three narrow ways.**

  `ExecutionTransition` gained a permitted subtype, `RecoveryWithheld`. The sealed hierarchy's
  published consumption model is to call the abstract `applyTo` each member carries rather than to
  enumerate the members — which is what every in-tree adapter does, and why an adapter that folds a
  batch needs no change. That is not the whole story. The type's own documentation sanctions an
  adapter that appends transitions to a log, and serializing a sealed hierarchy is the canonical
  reason to switch over it exhaustively; an appending adapter written that way does break, and must
  add an arm for the new member. Nothing existing changed meaning, and no member was removed or
  renamed.

  The `NodeAttempt` record gained a component, `withheldThroughDelivery`. It keeps a constructor at
  its previous shape, which defaults the component to zero, so existing source and existing compiled
  callers continue to work; code that pattern-matches the record by arity, or that constructs it
  positionally through reflection, must account for the added component. Zero is the honest default:
  an attempt recorded before this existed was never withheld by a mechanism that did not exist, so the
  subtraction it feeds is a no-op and the recovery delivery limit behaves for it exactly as before.

  An execution-store adapter outside this repository that maps attempt columns by hand will not know
  about the new one. It will neither fail nor corrupt anything: it will read the mark back as zero on
  every attempt, and recovery will charge withheld deliveries to the delivery budget exactly as it did
  before this change. The bundled SQLite adapter migrates itself, adding the column with a zero
  default and rewriting no existing row, and a binary predating the column still reads every row it
  wrote.
- `SourceSessionStatus` now carries a `deploymentId`, and `GET`/`POST`/`DELETE /v1/source-sessions`
  return it, so a client can attribute a listening session's runtime events to the graph that started
  it. The reference implementation reports the session's own id, which is the deployment its traversals
  run under. Live execution events (the `/v1/events` stream and `/v1/events/recent`) carry the same
  `deploymentId`, `null` for a one-shot submission that opened no deployment.

  **Breaking for embedders only.** The record gained a component, so the canonical constructor takes one
  more argument; the existing `of(...)` factories are unchanged and continue to name the session as its
  own deployment. An implementation of `RavenrootApplication` whose sessions run under a separately named
  deployment should use the new `of(sessionId, deploymentId, ...)` factories — a client matches events on
  this value, and reporting the wrong one shows it nothing. No HTTP field was renamed or removed.
- The Helm values schema now accepts only the documented image, Service, OIDC, resource, security,
  probe, storage and runtime-policy fields and rejects unknown or malformed values before rendering.
  Deployments that previously passed extra nested Kubernetes fields through `resources`,
  `podSecurityContext`, `securityContext`, or `probes` must remove them or apply them with a
  post-renderer or maintained chart/template customization before upgrading. The chart now fixes the
  packaged image to Pekko and requires non-root execution, RuntimeDefault seccomp, privilege escalation
  disabled, a read-only root filesystem, dropped capabilities, and positive pod/container identities;
  previously valid overrides of those named fields need the same customization path. The chart preserves its
  15-second program-timeout profile, validates configured bounds, and documents blank delegation to
  the Java-owned 5-second default.
- The server now resolves PostgreSQL connection, transaction, retention, lease, payload, inventory and
  definition-repair policy through one typed startup configuration. Non-secret settings support system
  properties before environment variables before documented defaults; database URL, role and password
  remain environment-only and are never copied into execution manifests or diagnostics. Deployment
  registry adapters share one programmatic policy, and the two ancillary SQLite stores share the same
  five-second connection-contention policy. The server and offline backup/restore CLI now also share one
  absent, blank and trimmed path rule for their audit and single-host execution-store directories.

  New server-managed executions use manifest format 3 to pin the generic persistence capacity separately
  from durable-result limits. Managed writes, recovery claims and timer claims require the immutable live
  store capacity to equal that pin, while a fenced matching idempotent replay remains a replay. Existing
  format-1 and format-2 rows have no trustworthy generic-capacity value and cannot perform managed writes
  after upgrade; they remain readable and retained. Unmanaged adapter compositions keep format 2 and
  their previous behavior.
- New executions use manifest format 4 to pin package decompression policy and the numeric envelope of
  pin-capable external-I/O nodes. WebSocket sends keep their accepted message, fragment, timeout and
  concurrency limits across recovery while destination and credential authorization remain live.
  Existing format-2 or format-3 executions with a non-bypassed `websocket.send` node are refused on recovery
  because those rows never recorded the accepted profile; unaffected old graphs keep their existing
  compatibility path. Node-package grants may set `maxDecompressionRatio` from 1 through 1000 and now
  default to 100 for new admissions; the source-compatible SDK capacity overload retains the historical
  1000 ceiling. Explicit non-positive or malformed HTTP byte ceilings now fail server startup instead
  of being treated as absent. Inbound sources can use managed services only through their current
  core-issued context, and stop, rollback, restart or undeploy revokes outstanding work and sessions.
  The context is a public SDK interface, but only the exact core-issued object is accepted as managed
  source authority. Its ingress facade is source-scoped and generation-fenced, may differ from the
  deployment-wide ingress object, and refuses new work after that source activation is retired.
- `mail.imap.consume` adds a stable `consumerId` and one-time `initialPosition=earliest|latest` bootstrap. Stable consumers resume from durable checkpoints across source-session and server restarts, including messages received while stopped; `earliest` remains the default and omitted consumer IDs retain the legacy deployment scope. UIDVALIDITY changes now stop the consumer instead of automatically selecting a new namespace: investigate the mailbox change, then deliberately choose a new consumer ID and initial position. Explicit stable consumer IDs require SQLite exclusive ownership and are currently refused on PostgreSQL, even with one replica.
- A graph node can now declare a bounded orchestration retry policy, and each retry is recorded as a
  distinct durable attempt with an increasing ordinal instead of the attempt history stopping at one. A
  node declares `retry.maxAttempts` together with `retry.retryOn`, the list of failure types it considers
  safe to retry, and optionally `retry.initialBackoff`, `retry.backoffMultiplier` and `retry.maxBackoff`;
  a node that declares nothing retries nothing, exactly as before. Only failures classified as retryable
  are repeated: a failure that reports its own outcome as uncertain, and a cancellation, are never
  repeated automatically, and a node's `retry.retryOn` list cannot override either — it widens only
  failures that say nothing about themselves. Cancellation, pausing, graph shutdown, a traversal that
  ends or suspends for an approval while a retry is waiting, and a used-up attempt budget all stop
  further attempts promptly, including during a backoff. A retry decision is committed before its backoff begins, so a restart
  resumes it rather than losing it and cannot turn one retry into two attempts.

  Runtime events and metrics now carry the attempt ordinal and report retries a connector performed
  internally separately from retries the orchestrator made, so an initial attempt, a retry and a
  connector's own retries can be told apart. The server's structured execution log carries both values;
  the HTTP event projection carries neither, and distinguishes a retry by its own event type instead.

  **Breaking, for consumers of the runtime event stream.** An attempt that fails and is going to be
  retried now publishes the new `NODE_RETRY_SCHEDULED` event **instead of** `NODE_FAILED`, rather than
  in addition to it. `NODE_FAILED` continues to mean that a node's visit failed, so a consumer counting
  node failures keeps counting the same thing and needs no change — that is the reason for the
  replacement. A consumer that instead counts *failed attempts*, or that treats every `NODE_FAILED` as
  the end of a visit, must now also handle `NODE_RETRY_SCHEDULED`: it carries the failure's
  classification in `publicReason` and the failure's class and message in the same author-facing text
  `NODE_FAILED` uses; the attempt ordinal is on the server's structured execution log, not on the HTTP
  event projection. A consumer counting `NODE_STARTED` as visits will overcount a retried node, because
  a visit now emits one start per attempt.

## Security

- External network and program operations now carry immutable per-operation limits for request wire
  bytes, encoded response bytes, decoded bytes, projected output, media type, content encoding,
  expansion ratio, deadline, and cooperative cancellation. Managed HTTP enforces the intersection with
  operator policy while streaming, and the first-party AI, MCP, Assistant, GitHub, OpenAPI, object
  storage, and GraalVM paths declare their supported representation and cleanup boundaries. Transport
  limits now remain active for every HTTP status while media validation is status-aware, and expanding
  storage/OpenAPI projections enforce a separate finite canonical-output ceiling. Managed responses
  carry the effective operator-intersected output ceiling through to final adapter projection, so a
  caller/profile-derived ceiling cannot widen operator authority after transport completes.
- HTTP routes now carry immutable request identity and client details through authentication, rate limiting, handlers, errors, and audit records without shared exchange attributes.
- Mail, Telegram, AMQP 0-9-1, and Kafka now reject reserved numeric destination addresses before
  credentials, clients, or sockets are used. The shared DNS-free policy covers IPv4, IPv6, mapped
  addresses, and zone identifiers, supports exact operator exceptions, and reports refusals without
  including the destination, credentials, or payload.

## Features

- A deployment can now choose which execution store Ravenroot runs on. `RAVENROOT_EXECUTION_STORE`
  selects the single-host store, which stays the default and behaves exactly as before, or the shared
  PostgreSQL store, which until now could be built and published but never reached from a running
  server. Selecting it needs a connection URL and nothing else; the server builds and pools the
  connections itself, and no credential reaches the store adapter or any diagnostic.

  Every claim a replica takes on an execution now carries a readable identity — the replica's name, a
  token minted at each start, and whether the claim belongs to the runtime advancing the execution or to
  the sweep that reclaims abandoned work — so an operator reading the process inventory can name the pod
  that holds an execution. How long a claim outlives its last renewal is now configurable within the
  bounds the store publishes.

  Configurations whose guarantees are not supported are refused at startup with the specific combination
  named, rather than started quietly: more than one replica against the single-host store, more than one
  replica while state that lives on a single pod is enabled, or a shared store selected together with a
  single-host directory. Backup and restore of the single-host bundle refuse under the shared store and
  point at the database's own procedure.
- An execution that can no longer reach any outcome — nothing running on its behalf, no join deadline
  armed, and a branch left parked at a fan-in waiting for an arrival that can never come — can now be
  reconciled instead of holding its admission capacity for the life of the process. Reconciliation ends
  such an execution through the same release every execution performs, so its capacity is returned
  exactly once and a new execution can be admitted, and it records the outcome as `FAILED` with the new
  `UNREACHABLE` termination reason on every surface that already reports `terminationReason`. That is a
  fault and stays in the failure series, unlike a cancellation; what the reason adds is that no node
  failed, so the thing to investigate is what stopped delivering. Operator cancellation remains a
  separate action with its own reason, and cancelling such an execution is now recorded as one: a
  cooperative stop has no next hop to refuse on a stuck execution, so the request used to end it with
  no termination reason at all, which reads as an ordinary failure. It is now recorded as the
  cancellation it was.
  Reconciliation is deliberately caller-invoked rather than driven by a background sweep, because the
  condition is established from positive evidence and never from elapsed time. This release exposes it
  on the application API only: there is no HTTP route and no CLI verb for it yet, so it is reachable
  from an embedding supervisor rather than from an operator command. Consumers reading
  `terminationReason` should treat a value they do not recognize as "not a cancellation".
- Add an optional Discord extension for bounded channel messages and signature-verified, durably accepted guild slash commands.
- Add an optional Slack extension for bounded outbound messages and verified, durable Events API and slash-command ingress.
- Add independent Microsoft Teams, Matrix, and Mattermost extension bundles with managed outbound messaging, durable provider ingress, strict tenant profiles, and operator documentation.
- Ravenroot can install an optional GitHub automation bundle for authenticated webhook ingestion,
  reconciled Project transitions and App reviews, exact-commit workflow observation, and read-only
  release metadata preparation under tenant-scoped operator profiles.
- Add bounded S3-compatible object listing and idempotent object deletion to the opt-in object-storage extension, including scope-bound pagination cursors, version-delete authority, managed retries, recovery declarations, and hardened XML projection.
- The workbench now supports durable, versioned Human Task confirmations with policy-bounded prompts and comments, accessible per-node attention counts, explicit generation-fenced decisions, and recovery from refreshes, network loss, and server restarts.
- A paused traversal now survives a restart. The hold is written down at the point the traversal
  actually stopped — between the node that has just finished and the node that has not yet started —
  together with the small amount of state needed to continue it, and it commits in the same
  transaction that records the traversal as waiting. After a restart the traversal is still reported
  as paused, and it is still paused: a hold produces no claimable work, so a recovery sweep finds
  nothing to dispatch for it, and nothing after the hold's boundary can run in any process because the
  stored state refuses to record a node as started on a waiting traversal. Only an explicit resume,
  authorized and audited exactly as before, continues it — rebuilding what it needs from the pinned
  graph and starting the node the hold withheld, which has never run, so nothing already completed is
  repeated. Cancelling a recovered hold ends the traversal and settles the hold; stopping a deployment
  or a process decides nothing and leaves the hold as it was. Settled holds are retained beside the
  process instance as the record of who decided what, and are removed with it.

  Not every point a traversal can be paused at can be written down. A hold is durable when the
  traversal is a single branch at a single completed node and the withheld payload is expressible in
  the payload type model; a traversal that has fanned out, one held at its very first node, one inside
  a loop or at a fan-in, and one carrying a payload the type model does not cover keep the earlier
  process-local hold, which a restart still forgets. Those holds behave exactly as they did before and
  report no error. Public documentation describes which is which and why.

  Durable holds are a declared store capability: a store that does not declare it keeps the earlier
  behaviour unchanged. The bundled SQLite store gains one table and rewrites nothing, so an existing
  database upgrades in place with no data migration; as always, a file upgraded by this release is
  refused by a build that predates it.
- The OpenAPI server extension now offers an explicit synchronous request/reply behavior alongside the
  unchanged asynchronous ingress behavior. Synchronous replies are correlated and deadline-bound by the
  runtime, must traverse the declared `respond` command, and are validated against digest-pinned OpenAPI
  status, header, media, schema, and byte constraints before reaching the HTTP caller.
- Ravenroot now durably retains the exact canonical GraphML document behind every accepted execution. The document is stored before the execution that references it, and acceptance is refused if it cannot be stored, so an accepted execution is always one whose graph is retained rather than one whose graph exists only in the memory of the process that accepted it. Documents are scoped to a single tenant, and identical documents submitted repeatedly within a tenant are retained once while distinct documents are never confused with one another. They are held alongside execution state, so an existing backup captures them and a restore returns them with the executions that name them. Reading a retained document back to resume work is not part of this release and arrives in a following change.
- Ravenroot now records, for every accepted execution, the dependency set that execution was actually resolved against — the exact document it was accepted with, the submission policy and unknown-behavior stance it runs under, the graph and traversal limits in force, the engine and store it was admitted on, the program runtime composed with it, and each installed node package by id together with a digest of its declared version and SDK contract. The record is written before the acceptance that references it, so an accepted execution always has one; it is immutable and scoped to a single tenant; and it holds only references, versions and digests, never a credential or an authorization snapshot. Before an execution is first dispatched and before it is recovered, resumed, restarted after a hold or taken over by another worker, that record is read back, checked against the digest stored beside it, and compared with what the running deployment resolves now. Anything that differs — a changed limit, a changed policy, a node package at a different version, a missing or damaged record — refuses the work with a diagnostic naming what differs, rather than quietly running the same graph with different behavior. Refused recovery work is left claimable rather than discarded and the reason is logged, and retention will not remove a record while its execution still exists. Records left behind by a refused submission or by a retired execution are reclaimed by an explicit tenant-scoped operation, which no operator command exposes yet. `GET /v1/executions/{id}/manifest` reports one execution's record identity and whether this deployment still matches it, naming the dimensions that stopped matching but never what they changed to and never how many node packages are installed — that describes the deployment rather than the caller's execution, and stays in the server-side diagnostic a refusal logs. Four limits are stated rather than implied: this checking refuses a mismatch rather than restoring the recorded values, and it only happens where a deployment composes a record store, so an application that composes none still resumes under whatever its process holds; a node package is identified by its id together with a digest of the version and Node SDK contract it declares, and not by a digest of its content, so a package republished under an unchanged version is not detected; a program artifact's approval state is deliberately re-checked at execution rather than pinned, so revocation keeps working; and executions accepted before a deployment turns this on have no such record and are refused by the paths that verify rather than being reconstructed from today's environment.
- Ravenroot now keeps a durable, tenant-scoped inventory of process instances and their traversals, so
  work already accepted before a restart remains discoverable afterward through `GET
  /v1/executions/inventory`, `GET /v1/executions/{id}/traversals`, and the new `ravenroot inventory` and
  `ravenroot traversals` CLI commands — the CLI commands read the tenant's whole answer in one call rather
  than a partial page. Each instance reports a recovery status — active, waiting, interrupted, parked, or
  terminal — computed from its stored state rather than a second record that could fall out of step with
  it, and all four of these listings report how far back their answer is complete so a caller can tell a
  missing instance from one removed by retention. Terminal instances become eligible for removal after a
  default seven-day retention window, but no operator-facing surface performs that removal in this
  release, so every terminal instance stays discoverable regardless of age until a later change exposes
  it.
- Ravenroot now offers an independently installable, provider-neutral confined Git workspace node
  package. Operator profiles fix the writable root, remote, base and issue-ref authority, Git
  executable, credential reference and resource bounds outside graph content. The package provisions
  one durable task workspace from a freshly fetched immutable base, integrates only its clean approved
  commit through deterministic merge preflight and a compare-and-swap of the recorded issue ref, and
  verifies the accepted commit or its exact full tree in bounded freshly fetched base history. Durable
  fenced association records reconcile crashes without replaying uncertain ref mutations, while a
  minimal Git environment, invocation-private credential socket, bounded output, cancellation-aware
  process-tree reaping and strict path/config validation keep credentials, ambient Git behavior and
  unrelated repositories outside the node's authority.
- Ravenroot now provides a policy-driven publication boundary guard that checks an exact typed candidate
  against a digest-pinned, operator-owned profile before an external effect. Declarative rules cover

- Ravenroot now ships a first-class `human-task` node. It parks a process without retaining a live

  tenant-scoped paginated inbox and generation-fenced decision API, and resumes through a fresh

- The View menu can now close every currently open document in one safe action, with aggregate choices for unsaved changes and active local source sessions while later-opened documents remain untouched.
- Ravenroot now publishes `ai.ravenroot:ravenroot-extensions-all` as a one-dependency Maven pack for every production first-party node package. The pack pins the complete reviewed extension set to one Ravenroot version while preserving explicit application or operator activation, package-scoped service grants, and the default distribution and OCI boundaries.
- The design editor gains two additional automatic arrangements, `Arrange — Hierarchical (new)` and
  `Arrange — Layered (top-down)`, next to the existing ones in the Layout menu. Both place nodes on
  discrete layers, reserve room for node labels, route edges in channels between layers, and carry
  backward edges in dedicated tracks outside the drawing instead of across it; one flows left to
  right, the other top to bottom. While the top-down arrangement is displayed each node's name is
  painted beside its card rather than under it, so the downward channels stay clear, and it returns
  under the card as soon as another arrangement or render mode is chosen. The existing
  `Hierarchical`, `Flow`, `Organic` and `Keep positions` arrangements are unchanged.
- Centralize Human Task authoring, inbox, payload, retry, and recovery limits in one typed server policy with property and environment configuration. Effective catalog bounds and durable task snapshots keep UI validation and restart behavior aligned with the policy that accepted each task.
- Add a reproducible whole-repository operational-configuration inventory and drift guard so every fixed candidate is reviewed before it can become an undocumented deployment policy. Startup parsers keep their documented defaults while rejecting malformed explicit authentication, SSE, assistant, execution-store, artifact-lifecycle, and unknown-behavior values. The bounded scanner recognizes `get`, `await`, `tryAcquire`, `tryLock`, `waitFor`, and `awaitTermination` calls that use its supported explicit `TimeUnit` argument forms, plus cumulative budget assignments; other method names, dynamic or statically imported units, and receiver-type inference remain outside that pattern. Newly discovered production candidates remain pending semantic review. Graph limits now expose the eleven previously embedded structural budgets through bounded environment bindings, and graph-limit parsing rejects out-of-range values without retaining raw input in diagnostics. All 25 graph settings are carried consistently through Compose, Helm values/schema/templates, and raw Kubernetes; blank carrier values continue to select the typed Java defaults. Human Task now uses one typed Java default authority for all 27 settings across Compose, Helm, and raw Kubernetes; 27 duplicate Helm defaults were removed, and exact constructor, resolver, schema-edge, and restart-pinning evidence guards the inventory classifications.
- Visual groups let authors collapse, expand, name and move related workflow nodes while preserving the executable graph. Group definitions travel with GraphML, and each workspace document retains its own presentation, viewport and focus. Design provides undoable grouping edits; Monitoring shows real member observations without introducing runtime group nodes.
- Execution manifests now persist the resolved graph, managed external-I/O, and durable-result limits that were accepted for each process. Restart, recovery, approval, and Human Task continuations reuse those immutable values after deployment defaults change, while destination authorization and credential revocation remain live. Existing format 1 manifests remain supported only when their original digest and trusted graph behavior prove that the newly required values were irrelevant; otherwise continuation fails with a typed missing-policy refusal instead of substituting current defaults. PostgreSQL deployments can configure write-once manifest pin repair attempts with `RAVENROOT_EXECUTION_MANIFEST_PIN_ATTEMPTS`.
- Centralize program-authoring and GitHub operation configuration behind typed, validated authorities. Program runtime and authoring settings now support documented system-property precedence, the connected editor consumes the server's effective authoring limits, Graal resource-cache placement uses an attested optional supervisor extension, and durable GitHub operations refuse recovery under changed non-secret profile semantics while allowing credential rotation.
- Ravenroot can expose an optional authenticated WebSocket for acknowledged durable event replay and generation-fenced Human Task resolve, deny, and cancel commands; operators must enable its bounded listener and route it through the documented TLS proxy topology.
- Long waits and human tasks are now durable. A process can register a named handler — with its payload
  shape, correlation key and the roles or scopes a resolver must hold — and park on it without keeping
  anything alive; the wait, its escalation, its expiry, a denial and a resolution are all idempotent
  durable transitions. An authorized trigger resolves the handler and starts a new traversal of the
  same process, which any worker can pick up, so a human task created before a complete server shutdown
  can still be authorized and resolved after the restart. Duplicate, late, cross-tenant and
  unauthorized triggers are refused the same way every time and recorded in the security audit trail,
  and execution events and the activity view now name the handler alongside the process, traversal and
  node invocation. Execution-store adapters declare the new capability, and adapters that do not
  support it report that instead of failing silently; the local SQLite store gains one forward-only
  schema migration and upgrades in place.
- Agent runs now use durable, process-rooted authority grants and finite budgets for turns, tokens,
  elapsed time, cost, tool calls, delegation depth, and team fan-out. Reservations survive approval
  waiting and restart without resetting spend, child grants must be strictly attenuated, and an
  authenticated runtime-wide kill switch invalidates old permits. The packaged server provides finite
  defaults and first-party agent packages must receive the explicit `agent-resources` capability.
- Ravenroot gains a durable, fenced authority for controlling a deployment's lifecycle. Eight commands
  — start, pause, resume, drain, stop, undeploy, cancel and restart — are each answered by one of nine
  typed outcomes rather than by an exception, with an operator's decision pinned to the exact lifecycle
  generation it was made against so a command that arrives after someone else has acted is reported as
  stale instead of silently overwriting the newer decision. A deployment now distinguishes being paused
  from being drained, and a client-chosen idempotency key covers the generation, so retrying the same
  words after the lifecycle moved is reported as a conflict rather than replayed as if it had been
  applied.

  Every accepted command records its key, the generation it was decided against, the generation it
  produces, the desired state, and the owner and fence that will carry it out before anything touches
  the runtime, so a process that dies mid-command leaves a decision that can be finished rather than an
  effect nobody can find. A reconciler resumes those decisions after a restart or a takeover, and the
  action happens once: at most one process holds a deployment's lease at a time, a superseded owner's
  writes are refused from the moment ownership moves, and the runtime port is required to be idempotent
  for a generation. A lifecycle transition on one deployment cannot reach the engine its siblings share: the widest thing
  the runtime port can do is release that one deployment's own domain, sources and in-flight work.
  An adopter who wires the SQLite adapter gets all of this durably, in the same database file the
  execution store already uses, added as four new tables without altering anything that was there.

  The deployments this process hosts are now what that authority reaches. A pause holds admission while
  the deployment keeps its activation, a cancel or a restart draws a barrier that ends the work admitted
  before it and admits everything arriving afterwards at the new generation, and an arrival that races
  the barrier lands on exactly one side of it — never on both, and never on neither.

  No externally published contract changes in this release: the HTTP routes, CLI verbs and OpenAPI
  document keep exactly their current behavior, and no command in this vocabulary is accepted by a
  running service yet.
- The workspace now gives every document a durable identity and explicit draft, Test, or deployed
  provenance. Authenticated tenant workspaces restore their documents, order, selection, presentation,
  and lifecycle mode from versioned browser storage without persisting runtime handles. Test and
  deployed snapshots are read-only until explicitly forked into a new draft, while offline and legacy
  service documents remain visibly session-only and are never silently adopted into a tenant scope.
  The authenticated configuration response now supplies that exact tenant scope from request-local
  principal state, including under concurrent requests, and the UI suspends tenant-bound actions while
  an authentication change is pending or cannot be restored.
- Ravenroot now documents and demonstrates what a backup of the shared PostgreSQL store restores. A dump
  and restore is shown to preserve every durable family the store holds — graph definitions and their
  bindings, pinned manifests and their node packages, executions with their traversals and attempts,
  leases and claimed work, idempotency records, the event journal with its outbox and inbox positions,
  the process inventory, execution results, every durable continuation, and deployments with their
  versions, command ledger and lease — together with the retention floors that say how far back each
  answer is still complete. The reference explains what a full and a data-only restore each require, and
  why a restore is verified by reading the store back through its own interfaces: a manifest separated
  from its package rows violates no database constraint and is still refused as damaged when it is read.
- The shared PostgreSQL store now carries the durable continuations a long-running execution depends on:
  named handlers and their wait and re-entry, scoped tool approvals, first-class human tasks with their
  embedded confirmations and authorized attention queries, operator holds on a traversal, and
  process-rooted agent authority budgets. Each of them commits in the same transaction as the execution
  transition beside it, so a process recorded as waiting is always waiting on something that exists, and
  a resolution and the work it authorizes arrive together or not at all. Correlation and deduplication
  keys stay unique across hosts because the database decides the winner rather than a check performed
  before the write.
- The shared PostgreSQL store now holds the deployment registry, so several Ravenroot hosts can agree on
  what a deployment is meant to be doing and which of them is entitled to advance it. Deployment intent,
  its graph versions, the command ledger and the ownership lease live beside the executions they govern
  in the same database, and a host whose lease has been taken over is refused with its stale fence
  rather than allowed to write. The registry's tables arrive as a second schema step, so a database
  created by an earlier build is upgraded in place rather than rebuilt.
- Ravenroot now offers a durable shared PostgreSQL persistence adapter, so several Ravenroot processes
  on different hosts can advance the same executions against one store. Exclusion rests on database
  transactions and row-level compare-and-set rather than on a file lock, so exactly one fenced owner can
  advance a process instance while competing hosts are refused; schema migration is safe under
  concurrent startup and refuses a database newer than the running build. The adapter is supplied a
  connection source by the deployment and never sees or stores a credential, URL, or certificate.
  Operator documentation covers supported topology, TLS, pool sizing, migration, backup and restore,
  retention, and the durability and high-availability limits that apply.

## Fixes

- Execution streams now share a versioned envelope with explicit live and durable variants, exact cursor IDs, matching headers, and retained legacy type compatibility. OpenAPI describes SSE framing and retention controls; the CLI can decode captured streams without starting a runtime.
- Set the JDK HTTP request-header cap when the server test JVM starts, before any bare HTTP fixture can
  freeze the process-wide parser setting. The existing runtime startup check remains in place for
  embedded deployments that do not inherit the Maven test configuration.
- A join timeout now measures active execution time and excludes any interval during which an operator
  has paused the traversal. Pausing stops the join's deadline and records what is left of its budget;
  resuming gives the join exactly that remainder, so a traversal held for longer than its remaining
  join timeout no longer fails the work the pause was protecting. A join reached while the traversal
  is held records its budget without starting it, repeated pause and resume cycles charge the join
  only for the time it was running, and no scheduled task is left behind by a pause, a resume, a
  cancellation, a join settling, or a deployment stopping.
- The sandbox supervisor CPU red control now proves its intended assertion deterministically while a
  separate measured real-process probe records when host CPU service cannot satisfy its deadline premise.
- Ravenroot now resolves one operator-owned graph-document byte limit and enforces it consistently in the workspace, HTTP and structured submissions, core admission and recovery, and durable graph-definition writes. Configure `RAVENROOT_GRAPHML_MAX_BYTES` as an integer byte count; the default is 10 MiB and the hard ceiling is 256 MiB.
- Existing edge changes now follow the Inspector Autosave preference, including coalesced text undo, immediate discrete edits, guarded invalid drafts, and explicit new-edge creation.
- Inspector saves and autosaves now retain each document's selected Design arrangement, positions, viewport, selection, and compatible edge routing.
- GraalVM cancellation cleanup tests now synchronize with supervisor-session publication and settled
  invocation cleanup, removing a scheduler-dependent assertion while retaining exact termination and
  reaping checks.
- The half-open barrier re-drive test now synchronizes blocked work entry and accounts for
  cooperatively cancelled work until its active node returns, removing a scheduler-dependent failure
  without changing deployment lifecycle behavior.
- Served configuration responses that include Human Task policy now contain exactly one complete JSON
  object, so authenticated workspaces can consume their configuration without trailing data.
- Human Task recovery ignores late exact-task and decision responses after the selected task,
  authentication, service, or document lifetime changes, and the restart harness returns through the
  fresh node Inspector without reconstructing deployment state.
- Fix the IMAP consume contract fixture to await durable checkpoint completion after ingress receipts.
- Fix the orchestration retry timeout test to await timeout registration and parked-join readiness.
- Fan-in join deadlines now remain effective while the first durable branch report is being written.
- Make JDBC cleanup admission tests wait for runtime cleanup reservations to settle before reusing capacity.
- Browser catalog fixtures now provide the service configuration required before catalog results become authoritative.
- Catalog failures now wait for their own workspace authority decision instead of disappearing during connection setup.
- Delayed authorization failures now invalidate only the bearer credential generation that issued the rejected request.
- Fix the join pause cancellation test to await actual scheduler registration before firing.
- IMAP admission recovery tests now order transport failure independently of the query watchdog.
- Discord sends now release node and shared-profile capacity before publishing their terminal result.
- Preserve the selected node and active Inspector editing control after automatic or manual node saves, so consecutive property edits no longer require selecting the node again.
- Keep Test and Run execution monitoring in the originating editor document without opening a read-only Test copy or changing the active document.
- Graph editing now consistently deletes the live pointer-selected nodes and edges with Delete,
  Del, Canc, or Backspace as one undoable action, while preserving native editing and dialog keyboard
  behavior and keeping read-only presentations protected.
- Runtime controls now call the authenticated execution Pause, Resume, and cooperative Cancel APIs,
  reconcile every response from authoritative execution state, and fence duplicate or stale document
  commands. Process-local source Stop remains distinct, while unavailable deployment Stop and global
  Shutdown controls are disabled with accessible explanations instead of simulating success.
- A graph that contains an IMAP, Kafka or AMQP consume node now starts from the editor. A node behavior
  is handed the values of the properties its own node type declares, and no longer the presentation data
  the editor writes on every node it saves, nor platform-owned flags such as the bypass switch. These
  three sources refuse configuration they do not recognise, which had made every editor-saved graph
  containing one of them impossible to start: only hand-written GraphML that had never been opened in the
  editor would run, and unticking a node's bypass box did not undo the breakage.

  Graph validation now refuses a node property that differs from one the behavior declares only by case,
  naming both spellings, so a misspelled property is reported when the graph is inspected instead of
  being accepted and then ignored at run time. Every other undeclared property is preserved and passed
  over exactly as before.

  Authors of third-party node packages should note that a behavior now receives only the properties its
  own descriptor declares; a behavior that read a property it did not declare will no longer see it.
- A graph whose entry point is an inbound source now shows its activity in the editor. Starting a
  listener session used to produce a lifecycle pill and nothing else — no node ever lit up, monitoring
  stayed empty, and the `log` node's output never appeared — however much traffic the source actually
  admitted. Nothing was wrong with the run: each admitted message started its own traversal, completed
  normally and published its events. They were attributed to nobody.

  Two identity gaps caused it, both about the same thing: a long-lived source produces an unbounded
  series of traversals whose ids nothing can know in advance. The reference monitor resolved ownership
  only for traversals a caller had submitted, so it withheld every event a source produced from the very
  tenant that started the session; ownership is now resolved through the deployment the event names, for
  that tenant's own deployments and no other. And the editor attributed events by matching a single
  execution id it was told when it pressed Run, which a source never supplies; it now binds a listening
  document to the deployment its session runs under, leaving Test and Run on the unchanged execution-id
  rule. Fixing the attribution restores the `log` node's output with it: that output was always produced
  and published, and only ever dropped on arrival.

  Two behaviours worth knowing. A node's colour reports the node rather than the last event about it,
  by precedence rather than recency: it stays failed once a message has failed there and until another
  message enters the node, is active while occupied, and otherwise shows the last settled outcome. A
  sibling message completing a moment later therefore cannot repaint it green, and a cumulative failure
  count on the node's caption keeps the record after the colour has moved on. The canvas repaints at
  most once per frame from that aggregate, so a fast source cannot outrun the view.
- The Undo and Redo tooltips again name the change they would reverse instead of showing the generic
  help text for the command. A command may now describe itself from the current document state, and
  that description is what the toolbar and the application menu show; the keyboard shortcut reference
  keeps the command's static help, and controls that explain an unavailable runtime capability keep
  theirs. Previously the periodic command refresh overwrote the specific description that had just
  been written for the history controls, so every step was offered as "Undo the last change".
- Adding a node from the Inspector keeps the new node open in the Inspector again instead of closing it
  a moment later, so its properties can be reviewed and edited straight after **Add node**. Saving an
  existing node now also updates the status shown beside its controls: the END node's warning about an
  undeclared join disappears once a kind of arrival is saved, and clearing a declared runtime
  concurrency limit reports the catalog's inherited default rather than the value that was just
  removed.
- A deployment barrier no longer reports an arrival as ended when that arrival was still awaiting
  dispatch and is refused instead, so each arrival racing a barrier is accounted for exactly once. On
  non-durable ingress, an arrival whose generation a barrier closed before dispatch now stays refused
  even if a later pause and resume move admission on before it resumes, rather than being dispatched
  into the generation the barrier ended. Durable ingress does not yet have that guarantee (#325).
- Operational configuration audits now reconcile source identity changes explicitly, preserve reviewed evidence, classify new candidates, and report deterministic follow-up ownership without silently retiring prior inventory rows.
- Dependabot security and version updates now run through development pull request checks instead of
  entering release-promotion gates.
- GraphML compatibility rejections no longer expose parser or scalar-mapping exception details through
  their cause chains, while retaining safe incident-correlated diagnostics for operators.
- Generated catalog property controls now expose stable label, hint, and state relationships to assistive technologies without changing their validation or save behavior.

## Documentation

- Clarified how Ravenroot's GraphML importer preserves raw property values while normalizing modeled fields.
- A new integrator-guide quickstart shows how to embed the read-only graph viewer in an external page,
  with a complete host page and host server that were built from the guide's own text and run against a
  live Ravenroot instance rather than reasoned about. Until now seven pages carried `embed` in their
  name without a single code block between them, so the shipped embed surface — five HTTP endpoints,
  the `ravenroot.embed/1` postMessage protocol, and the bootstrap script — had a documented contract but
  no worked example. The guide states in its opening lines that what is embedded is the read-only
  projection and not the authoring editor, and it records the constraints that decide an integration
  before any code is written: the viewer is served only to an iframe navigation, both the viewer and
  parent origins must be canonical HTTPS origins, and `/v1/embed/sessions` and
  `/v1/embed/acknowledgements` refuse any request carrying a cookie, an `Origin` header or a
  `Sec-Fetch-*` header — which includes requests made with HTTP clients that add such headers on their
  own, such as Node's global `fetch()`. It also documents that the host's `ACK` is only valid once the
  integrator's own server has acknowledged the channel, that the theme is fixed by the registration or
  the reader's `prefers-color-scheme` and cannot be set by the host, and that `FAILED` reports that a
  session ended without reporting which of the four failure kinds ended it. `embed-protocol.md` remains
  the contract, and the two pages now link to each other.

  The page also records that the canonical-origin rule is enforced when a session is created rather than
  when a registration is written: a registration carrying a non-canonical parent origin, or one equal to
  the viewer's, is stored and then refuses every session with `403 EMBED_SESSION_UNAVAILABLE`, which is
  the same code an unknown or revoked registration produces.
- The public documentation now provides persistent section navigation, responsive mobile access, and a readable Ravenroot theme that follows the reader's system light or dark preference.
- `BehaviorRegistry.find(String)` now documents its configuration-independent lookup limit and points property-dependent callers to descriptor-aware node creation.
- Clarify that `visitedNodes` and `visited-nodes` report unique traversal membership, while their iteration or presentation order is not execution chronology; use invocation or event history when ordering or repeated visits matter.
- The engine-level property that domains close concurrently rather than one after another is now proven
  by a deterministic, synchronization-based conformance test in place of the previous check, which passed
  without ever being able to detect a serialized close, and the per-domain close bound behind the
  deployment shutdown budget is now measured and cited: 20 seconds, from each supported execution
  engine's own two-phase (stop, then cancel-on-timeout) close bound. Reading the pod's actual shutdown
  path against that engine-level property found that a pod currently closes its active deployments one at
  a time, not concurrently, so its worst-case graceful-shutdown time grows with the configured cap on
  active long-lived deployments per pod rather than staying fixed; the shutdown-budget documentation and
  the packaged Kubernetes and Helm deployment manifests are corrected accordingly, and a new test pins
  today's one-at-a-time shutdown behavior so it cannot silently diverge from the documented budget again.
