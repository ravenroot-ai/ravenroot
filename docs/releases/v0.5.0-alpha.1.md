# Ravenroot 0.5.0-alpha.1

Ravenroot 0.5.0-alpha.1 delivers the work integrated since `0.4.1-alpha.1`. It contains breaking
changes: read *Breaking changes* below before upgrading, together with the compatibility policy and
the operator guides. Pin every Maven and OCI dependency to this exact version, and use an immutable
container digest where deployment reproducibility matters.

## Breaking changes

- Explicit Workspace lifecycle nodes and named Agents replace the generic workspace-agent node.
  Workspace scope and container reuse are independent, with durable cancellation, pool scheduling,
  operator-sized capacities and supervised workers. A separate PostgreSQL-backed runner coordinator
  can scale independently of workers; the full graph/authoring server remains single replica.
  Upgrade requires stopping writers, taking a verified backup, starting the upgrade so it applies the
  complete SQLite schema transition through migration 32 or PostgreSQL transition through migration 12,
  and replacing old generic graph nodes with a Workspace plus Agents using typed workspaceRef. Before
  restoring traffic, check readiness, list a known pre-upgrade task, exercise a dry-run reconciliation,
  and test capability revocation across a replica restart. Ordinary Agent graphs are unchanged. Writable
  model-backed execution requires an approved model profile, Landlock-capable Linux and positively
  verified storage quotas; unsupported hosts fail closed. Trusted-local `service.sh start --runner` and
  restart supervise a tokenless in-process worker; public loopback users and the private workload
  channel remain structurally separate. Stop includes retained Workspaces. CI now requires secretless
  native model-protocol, Landlock/seccomp and XFS evidence; live-provider smoke is a separate owner-only
  local opt-in and never a merge prerequisite.
- Add an explicitly selected Kubernetes-native governed runner with owned Pod/PVC lifecycles,
  positive quota/security preflight, credential-separated model execution, fenced report-only
  recovery, native Workbench/API/CLI evidence and secretless real-cluster CI. The initial supported
  backend is fixed-size ext4 local PV storage; checkpoint/restore and automatic driver migration are
  unsupported. Upgrade servers, coordinators and workers together before publishing native profiles:
  new persistence/assignment envelopes preserve Kubernetes identity and older workers are refused.
  Existing profiles default to the Docker driver; Helm worker pools now require an explicit driver.
- Design arrangements now treat each collapsed visual group as one authoritative layout unit, while Design and Monitoring preserve independent document views until the new Render action explicitly recomputes the active mode. Saved workspaces retain both views, the selected Design arrangement, Monitoring forces, and draggable group geometry.

## Features

- **Multi-release JDBC driver jars.** The JDBC extension now loads the multi-release driver jars that
  current vendors publish, so a bundle can use PostgreSQL JDBC 42.7.12 and the security fixes released
  since the vendor moved to that packaging. Each jar is still verified against its pinned SHA-256, then
  resolved once, for the release Ravenroot targets, into the single flat image the driver is defined
  from, whatever JVM runs Ravenroot. A jar that admits more than one reading of what its image contains
  is refused before the driver initializes, as `JDBC_DRIVER_AMBIGUOUS`; bytes that do not match the
  pinned digest are refused as before. Driver jars that carry no versioned entries load unchanged.
- Ravenroot now includes a pure, deterministic `bigint-op` core node for bounded exact integer copy, arithmetic, comparison, and graph-authored counter-machine steps without a program artifact or sandbox lifecycle.
- Ravenroot now includes Register Machine Profile v1 with a bounded static validator, constructive conformance tools, transparent editor presets, exact long-decimal round trips, and executable arithmetic, cancellation, observation, and incremental-Pi examples.
- Human Task operations can now enforce graph-authored responder roles and scopes, with tenant-local
  administrator overrides that require a reason and produce separate audit evidence. Typed classic,
  confirmation, form, custom, and external presentations are supported; custom and external hosts use
  registered secret-managed profiles with constrained origins and capability handling. Operators can
  inventory attention work and perform idempotent administrative reconciliation. Upgrades automatically
  add the presentation and capability-revocation records; follow the operator guide's backup, readiness,
  known pre-upgrade task, dry-run reconciliation, and replica/restart revocation checks before restoring
  traffic.
- The Workbench now provides a capability-driven global lifecycle console for authoritative deployment and process selection, generation-fenced Pause, Resume, Cancel, Drain, and Stop controls, and post-command reconciliation that remains separate from Human Task settlement.
- Runtime activity observation now offers Output, Nodes, and Trace visibility modes. Output shows
  workflow output, failures, final state, and panel messages; Nodes also shows node starts and
  completions; Trace includes the technical event stream and its identifiers. The chosen observer level
  changes panel display only: it never changes GraphML or execution, starts at Output after reload, and
  applies to events that arrive after the selection.
- Ravenroot can now discover tenant-owned READY local deployments and issue revocable, expiring,
  fixed read-only embed grants under an explicit server-side origin policy. Existing durable embed
  registrations remain supported unchanged, while dynamic-only startup is available without a
  registration database.
- Graph documents and embedded viewers can now maximize without losing viewport or live-run state, while deployed visual groups retain member activity, flow indication, and node monitoring inspection.
- Embedded viewers can now attach to a running deployment for a read-only graph view with bounded live lifecycle and execution updates, while existing immutable snapshot registrations remain supported.

## Fixes

- A pull request into `dev` had regressed to publishing the required `ci-required` check from a small
  `admission` diagnostic tier, without the full test suite ever running on the pull request's head. This
  repository first tried closing that gap by removing the `pull_request` trigger for `dev` entirely and
  verifying the review candidate with a full run dispatched on its exact commit instead. That change was
  tested against real pull requests and reverted: GitHub's required-checks evaluation for a pull request
  only sees check suites from that pull request's own events, never a `workflow_dispatch` suite living
  on the same commit, so a pull request into `dev` was left with `ci-required` absent rather than green,
  and could never be queued or merged.

  `pull_request` into `dev` is restored and now earns the full tier directly from the classifier, not
  the retired `admission` diagnostic — a fork's pull request the same way as a repository branch's,
  without any manual step. The dispatched review-candidate run and the routed Dependabot dispatch
  continue to exist for verifying a commit before its pull request opens or before a Dependabot update
  can reach `dev`. The `admission` tier's retired jobs remain in the fast feedback workflow for every
  work-branch push, so contributors still see that signal on every push. The net capacity cost is one
  additional full run per change: once on the pull request's own event, once more when the merge queue
  verifies the integration commit.
- Deployment lifecycle clients now use the server's durable command contract. HTTP, CLI, and the
  Deployments window expose authoritative generations, send unique idempotency keys and required
  operator metadata, parse every typed command outcome, and reconcile state without replaying refused
  decisions. Legacy process-local and source-session deployments remain compatible, while durable
  Undeploy retains tombstone replay and removes its local runtime. Durable local IDs now keep a
  non-expiring tenant-scoped identity binding across complete restarts and command-ledger purge, and a
  second lost command response triggers authoritative read reconciliation without a third delivery or
  an invented outcome. Undeploy confirmation text now distinguishes permanent durable tombstones from
  reusable process-local registrations.
- The Monitoring graph now settles. Once node movement is no longer visually significant the layout stops
  and holds a stable view, instead of drifting through a long tail of imperceptible force motion. A
  runtime instance-count change still resizes the node and updates its collision size for the next
  layout, but no longer reheats or restarts an already settled graph, so live activity no longer keeps
  the view in motion. Dragging a node still reheats the layout so it can adjust around the new position
  and then settle again, and explicit layout and force-control changes continue to reheat as before.
- Graph admission and inbound-source startup failures now use shared, versioned, bounded diagnostics
  from inspection through runtime status and the Workbench. Starts revalidate their exact GraphML,
  declared source failure codes remain closed at package registration, unknown failures expose only an
  incident handle, and the original throwable reaches one privileged correlated record.
- Preserve deployed source-session monitoring across durable Human Task, approval, governed-runner,
  and pause continuations so resumed traversals remain visible in the owning Workbench timeline.
- # Hermetic MinIO acceptance supply

  - Wrap the real MinIO server and client acceptance fixtures in a repository-controlled Ravenroot-owned
    GHCR package, pin both by digest, and fail before the long backend build when either immutable
    image or the GitHub runner architecture is unavailable.
  - Keep the TLS, SigV4, versioning, pagination, durable-restart, and cleanup gate backed by the real
    provider while recording reproducible provenance and rotation instructions.
- The load-interleaved sandbox stability check now allows slower CI workers enough time to complete its first nested Maven workload.
- AMQP Human Task workflows now accept their catalogued recovery declaration, publish the resolved response with broker confirmation, and resume promptly when a failed lease renewal leaves a releasable lease behind.
- Launching a Test or Run no longer re-renders the Monitoring graph. The previous run's colours, instance
  counts and edge activity are cleared in place on the graph already on screen, so node positions and the
  zoom/pan view stay exactly where they were instead of the layout re-arranging itself on every launch; a
  cleared graph shows the same idle node size a freshly opened Monitoring view does. Dragging a node,
  arranging the layout explicitly, and the repulsion/attraction/speed controls still reheat the graph.
- Release automation now retains verified minor-promotion evidence across later Main merges and selects the current development audit source, so an already prepared but untagged release can complete only when its immutable version, tag, notes, and reviewed promotion evidence still match.
- Main-push backend regression selection now receives the exact preceding commit. If an accepted minor
  promotion reaches main before its immutable tag is created, recovery remains fail-closed: it requires
  the absent expected tag, the exact prepared version, and GitHub evidence of the preceding internal
  minor promotion. Tag validation accepts an existing target only when it identifies the exact recovery
  merge being validated.
